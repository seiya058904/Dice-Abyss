## 3. 原交互方法的范围与限制

原脚本使用真实 Continue、主导航点击、原生 select 的 ArrowDown/ArrowDown/Home，并检查 isTrusted；正式 12 对固定 AB/BA 交替，先一对明确标记的预热。没有自动重试、替换慢样本或剔除离群值。逐动作完整卡片、排序、存档、console/pageerror 断言未见实质驱动错误。

计时从 DOM 事件 capture 到第二次 requestAnimationFrame 回调中的 `performance.now()`。它包含同步事件处理、HTML 生成、DOM 替换、相关布局／恢复和回调调度等待，**不是单独 selector 时间，也不是完成 paint 的时间或 FPS**。`firstRaf` 与 `secondRaf` 参数是动画时间戳，不能把这些时间戳的差直接解释成 CPU 用时。Long Task 观察只是窗口内的附加记录，不测量各函数成本，也不证明没有被记录的成本就不存在。

原方法对实际按钮／下拉操作及 UI 真值有价值；在本次环境的 60–700 ms 分布和强顺序关联下，单凭它不能判断排序临时对象是否使 Chromium 更慢。也不能用此前 Node 的 1–2 ms 级 selector 收益解释或否认 100 ms 级交互差值。Node 证据、浏览器同步阶段证据、事件到回调证据必须保持各自口径。

## 5. 具体分配风险、低风险备选与最终决策

当前实现将过滤结果映射成 N 个 `{item,value}` 行对象，排序后再映射回物品数组。相较基线的 `filter + toSorted`，新增了 N 个短命对象和一个完整结果数组，留下更多 GC、间接访问与 JIT 行为的可能成本。缓存收益依赖比较次数：随机混合大背包能避免很多 itemValue 重算；全部主键不同、全部相同、已经排序或反序的数据，计算重用收益弱，分配就可能占上风。最终 Node 数据中 unique-level、equal、presorted/reversed 的负向已完整写入 `FINAL_REVIEW.md`，不能当作不存在。

若归因显示分配成本妨碍浏览器收益，一个范围更小的备选是：保留现有排名行和比较器，排序后把 `ranked[i].item` 写回本次 filter 新建的 `selected[i]`，最后返回 `selected`。这样可去掉最后一次 map 的新数组和回调，不写入调用方原数组，也不改变物品引用、相等排序、过滤、非法 sort 或旧合法稀疏字段的语义。它仍然分配 N 个 row，所以不能称为已经解决所有分配问题；本代理没有实施或测量此备选。

改用对象 Map 缓存或数值索引／TypedArray 可以继续减少某些包装对象，但会引入查表、索引间接访问或另一套数据结构成本，收益不能从对象数量直接推出。本轮不宜在现有证据不利时连续试多套实现再挑最快的一套。

建议根代理用已固定控制组和归因结果做一次决定：

1. 如果同源码对照也显示类似事件时延／顺序偏差，同时原版本对照的 selector 和包含它的 center 在浏览器中有清楚、稳定的收益，可以保留这个受测范围内的计算优化；发布说明只能声称得到直接测量支持的同步阶段改善，仍披露原交互负向与不确定性。
2. 如果 browser selector 或 center 回退，或收益不足以支持分配代价，回滚独立 selector 改动是更稳妥的本轮结论。次数下降本身不构成用户收益。
3. 如果要采用上述仅复用 filtered 数组的备选，应先明确它是新候选、冻结源码和次数，保留原候选全部结果，再走必要的正确性及一次受控验证；不要把新候选样本拼入原正式分布。
