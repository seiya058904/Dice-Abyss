## 2. 信息层级与真实提示

### 先认装备，再看立即后果，最后读条件

顶端仍是“装备比较”、候选装备和当前装备，身份关系明确。黄色“条件需权衡”保留了对单一估值的限制，没有把 `+82%` 呈现成确定的战斗收益保证。即时状态位于条件明细之前，玩家可以先判断换装是否削减当前生命、是否立即补盾，再继续阅读词条。

新区域使用普通标题、两行数值和细分隔线。它没有变成醒目的额外装饰卡片，视觉重心仍是数据。当前生命和生命上限并排显示，使 `165 / 165 → 165 / 224` 中“上限增加、当前生命不变”的区别可直接读出。

### 文案与本次画面事实一致

- **提高生命上限不等于即时治疗。** 图中的当前生命仍为 165，文字也明确不会随上限提高而恢复。
- **降低生命上限可能损失当前生命。** 自然战斗画面从 173 降至 165，提示明确写出 8 点损失及重新换回装备不会补回，既给数值，也交代不可通过换装反复撤销。
- **当前护盾和开战护盾分属两个时点。** 即时区域写 `3 → 3`，下方词条另写“进入下一场战斗”；“换装不重新发放开战护盾，已获得的护盾保留”避免把两行当作矛盾。
- **骰数只是必要条件。** “当前使用 1 颗战斗骰；骰数足够仍须满足对应触发条件”避免把解锁更多骰子写成必定触发。共鸣护盾下另有明确的当前不可触发及 Lv.2 解锁第二颗骰说明。
- **估值覆盖保持有名称的限制。** “基础生存估值”“近似计入”“未计入估值”等标签仍区分估值和实际词条；没有把条件百分比直接相加成当前生命或最终伤害。

已有 `comparison-browser-final/report.json` 的自然序列记录包含这次 8 点裁减：换装前 hp=173/maxHp=224/ward=3，换装后 hp=165/maxHp=165/ward=3；与所看截图相符。这里引用的是已有逐状态回执，没有将选定自然种子扩展为胜率结论。

## 4. 两种代码原生方案的实际取舍

| 方案 | 能解决的决策问题 | 主要代价或不足 |
| --- | --- | --- |
| A：只在原条件表标注当前骰数和不可触发限制 | 保留紧凑结构，说明当前构筑能否触发词条；适合沿用原有文字、数字与行分隔。 | 仍没有直接回答“现在装备后剩多少生命／护盾”；仅看生命上限与估值仍可能误会为即时恢复。 |
| B：增加“此时装备后的状态”区域 | 用前后数值明确当前生命、上限与护盾，并在真实裁减时指出损失量；重要后果更早出现。 | 增加纵向长度；单独使用它仍不能解释双同等词条在一颗骰时不可达。 |

**最终采用两者结合：**先显示即时生命／护盾，再在原有条件表中给骰数与具体限制。这样两个问题分别获得直接答案，避免把即时状态混进未来触发的词条百分比。接受增加滚动长度，保持关键即时后果在 320 初始首屏内；不用压小文字换取全部内容同时可见。

上述两种是代码原生的信息组织方案；本报告没有声称存在两份额外绘制的图像原型，也没有把方案取舍称为用户 A/B 实验。最终画面继续沿用项目的旧像素风，没有引入一套不同的卡片、渐变或插画视觉语言。

## 5. 为什么不需要额外位图

本次内容是随装备、当前生命、护盾和骰数变化的即时解释。原生文本、数字、箭头和 CSS 分隔线能够准确表达这些变化，并支持正常换行、缩放、复制和语义读取。现有字体与边框已经承担视觉风格；再增加背景图、图标贴图或静态信息图片不会补充新的决策信息，反而会增加资源体积和维护负担。因此沿用现有资源即可。

## 6. 边界与交付判断

没有发现新的实质视觉缺陷需要回到产品修改。保留两项明确边界：长比较页需要滚动；本次主要验证新增关键解释，未开展整页所有小字的重新排版或全面无障碍审计。

这些是软件渲染下的**模拟逻辑视口**。320／390 截图不等于实体手机触控、系统字体缩放或真实屏幕阅读体验；1920／3840 布局回执也不证明独立 GPU 帧率。屏幕阅读器、系统中文输入法、实体触摸手势、200% 浏览器缩放等不在本次只读校对范围内。
