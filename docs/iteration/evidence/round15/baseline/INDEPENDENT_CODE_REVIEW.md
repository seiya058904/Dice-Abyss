## 1. 恢复结算与记录位置

审读范围为 `src/deep-rules.js` 中 `abilityRoll`／新增 `abilityRecoveryNotes`，`src/engine.js` 中导入、记录起点及记录回填三处，以及 `tests/healing-settlement-record.test.mjs` 全部七项。

### 数值和触发顺序

原先的恢复计算按照 `sixthMend`、`resonanceMend` 顺序累加 `st.maxHp * st[key]`，最后对总和只执行一次 `Math.floor`。当前实现保持相同顺序、相同正收益条件和同一合计取整点。没有改为分别向下取整再相加；七项回归中的非整数生命上限案例专门检查了 383 与 382 的差别。

防御判定仍在伤害结算前通过 `abilityDefense` 获取。`resolveGuard` 仍根据本掷开始时的生命比例判断，不会因为后续治疗而重新取值。伤害、回响、穿盾、首掷追加、敌方阶段切换和盾量公式未动。完整本掷顺序仍为：

1. 抽取骰面，再取暴击／追击随机数；计算本掷属性和既有能力。
2. 结算对敌伤害与阶段盾，增加本方本掷护盾，并处理原有 `mod.healPlayer`。
3. 对未被击杀的敌人结算闪避、反击、护盾吸收、敌方既有特性及 `postRetaliation` 后置生命流失。
4. 仅在生命仍大于零时，依次结算能力恢复、暴击吸血天赋、装备再生。
5. 记录本掷结果；击杀后的经验、升级回复、战后回复、宝箱与幸运奖励继续在原位置执行。

新增逻辑没有随机数调用，没有移动原有随机数调用，也没有增加战斗转移。辅助函数仅从本掷的两个合法能力键生成固定文案。以完整反击／流失之后的存活事实回填记录，避免“先满足骰面条件、后来死亡”的本掷仍显示恢复已生效。满血时的能力依然可以被记录为触发，不宣称有正的实际回复量；这一点与原能力触发语义一致。

### 原日志顺序与 24 条截断

原记录可以写成“敌方前置机制、恢复前能力记录、两类恢复记录、恢复后能力记录、后续战斗记录”。新代码只在暂存期间移走两类恢复记录，分别保存原能力记录中的位置 `recoveryIndex` 和能力记录前的全局长度 `abilityNoteStart`。在最终生命已知后，于这两个长度之和处插回恢复记录。

从能力记录生成到回填之间，当前 engine 对 `mechanics` 只追加记录，没有删除、重排或提前截断。因此非恢复记录的相对顺序不变；恢复记录也回到原始位置。存活时得到原有字符串和顺序，死亡时只替换对应记录文字。

两处 `mechanics.slice(0,24)` 均在回填之后：首次写入 `lastRoll`，以及击杀奖励追加“追星”后的再次赋值。恢复记录的条数也与原实现一致，所以不会因“把恢复文案最后追加”而将其他记录挤出原截断位置。七项回归检查了攻击能力、恢复、守望及首掷回响之间的顺序；极端 24 条位置由这段源码的插入位置不变量支持，本复审没有另外运行构造压力测试。

### 保存和历史

`recoveryKeys`、`recoveryIndex`、`recoveryNotes`、`abilityNoteStart` 只存在于本掷局部变量／临时能力对象中，未加入 `state` 或 `lastRoll`。保存 schema、存档键、校验、迁移与事务入口未改。新文案远短于现有 mechanics 单条 80 字符上限，记录条数仍最多 24。

已有存档的历史 mechanics 不会在加载、锁定装备、背包查看或其他无关动作时被补写。新文案只在下一次真实 roll 转移中产生。七项测试还检查了输入不可变、完整 codec 往返、嵌套未知字段保留，以及重试以前的原历史记录。

### 七项测试的覆盖价值

七项分别覆盖：致死反击、存活且合并取整、盾后诅咒流失致死、满血与击杀、两类能力各自触发／不触发、记录原序与临时字段不泄漏，以及旧历史记录保留。测试使用明确标记为构造的合法状态；没有把这组案例当成自然死亡频率、胜率或平衡性证明。测试未替换引擎规则，也没有通过过滤整个状态来隐藏 RNG 或其他数值差异。

## 2. 背包名称搜索

审读 `src/inventory-query.js`、app 的 input／submit／导航／清除与 run boundary 逻辑、views 的表单与列表渲染，以及 `tests/inventory-search.test.mjs` 七项。补查 `inventory-dom.js`、`fusion-dom.js`、物品校验、既有回收确认和保存事务。

### 文本安全与结果真值

- 名称匹配使用去首尾空白后的大小写不敏感字面量 `includes`，没有正则构造、动态代码或网络行为。`.*`、方括号等输入不具有额外语义。
- 输入框的 value、已提交查询回显均经过现有 `esc`，查询内容没有拼进 CSS 选择器、HTML 属性名或动作名称；结果播报使用 `textContent`。
- `item.name.toLowerCase()` 的调用依赖合法物品结构。当前 `validEquipment` 强制名称为字符串且长度不超过 64，故正常加载、导入、生成的可玩状态满足该前提。表单也设置了 64 字符长度限制。
- 选择函数先过滤整个物品数组，再沿用原排序表达式和稳定排序，最后由 view 每页显示 60 件。它不会只搜索当前页，也不会把搜索结果写回 `s.player.items`。空查询的短路分支保留原三个排序模式的结果和相等项顺序。

### 保存和交易保护

`ui.inventoryQuery` 与 `ui.inventoryQueryDraft` 只在 UI 对象中使用；本次所有搜索路径均不调用 `transition`、`act`、`saveGame`、`saveImportedGame`、Web Locks 或 localStorage 写入。输入事件只更新草稿，不逐键重建 DOM；submit 才应用查询、重置页码并重绘。只读排序所用 `itemValue` 是纯计算，不消耗 RNG。

submit 阻止原生导航，并在恢复保护界面、打开的对话框或非背包页面中拒绝应用查询。它没有绕过任一保存锁／快照比较。即使与等待中的既有事务处于同一 UI 生命周期，查询只改变显示状态，不能改变事务已经捕获的旧 state、确认目标或来源物品。

自动安全回收继续对完整 `state` 调用 `salvagePreview(s, undefined, false, true)`，不接收搜索结果。确认框仍从该完整预览捕获 ID；最终 `act` 与引擎重新核验目标和保护条件。新文案明确告知“全背包检查（不受搜索与筛选影响）”，避免用户将回收理解为只作用于可见结果。装备、锁定、稀有度、战利品保护与溢出确认均保持原路径。

### 生命周期和键盘

普通导航保留已提交查询及尚未提交的草稿。战败专用准备入口同时清空名称、草稿和旧品质。清除名称保留装备位／品质，清除全部筛选清空三者，并回到第一页。新旅程、导入、恢复和跨 run 同步都经过 `clearRunSelections`，不会继承另一段旅途的搜索。

搜索输入与提交按钮有稳定 ID，原 `captureInventoryPosition`／`restoreInventoryPosition` 可重新找到并恢复对应控件焦点；明确结果变化使用 reset 路径，从列表顶部开始。全局空格掷骰还要求 game view 并排除 input 等交互元素，名称输入不会被误认为手动投骰。

七项测试覆盖选择纯度、字面量／转义、空搜索旧排序、万件全背包与分页、无结果恢复、专用／普通导航区别，以及清除操作不保存。它们未实际发送原生浏览器的 IME／submit 事件；应以整合者的浏览器测试确认提交、中文输入过程、焦点、窄屏与 4K 的最终表现。本复审不把源码阅读冒充上述浏览器验收。

## 3. 冻结后所需的既定门禁

1. 保留现有完整关键测试并完成默认模块与全部实际细项计数；不要使用旧候选或仅模块 wrapper 的数量代替真实细项。
2. 对冻结 engine 重跑既有恢复记录完整状态差异脚本，关闭本报告首项源身份限制。只允许明确的死亡恢复文字差异，不排除其他状态字段。
3. 完成整合者已安排的搜索真实交互与保存未写入核验，以及最终标准 1,000＋50 模拟。标准零死亡政策的结果相同不能单独证明死亡文案修复正确。
4. 性能结论仅由独占、匹配条件的正式测量给出；本次轻量源码审查不支持吞吐、输入延迟或 FPS 改善声明。
