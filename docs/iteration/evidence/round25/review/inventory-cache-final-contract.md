# 下一轮维护约束：库存分页缓存

`src/inventory-page.js` 只保存应用最近一次局部库存渲染得到的完整筛选/排序结果；目前仅 `inventory-page` 事件在 `src/app.js` 中传入 `inventoryPageOnly:true`。命中必须同时满足：同一个已提交 `state` 对象、同一个 `state.player.items` 数组、同一个 `runId`，以及装备位、品质、规范化且转小写的已提交查询词、规范化生存条件、排序方式全部相同；页码和未提交输入草稿不在键中。应用还要求当前确实处于已渲染该 state/run 的库存页，且无全窗口重置、恢复保护、对话框、提交中、动画忙碌或临时展示状态，才进入这条局部路径。任意全页渲染回退都会先 `clear()`，且普通 `gameView` / `center(s, ui)` 不回填缓存，因此初次进入库存或任意全页重绘后直接第一次翻页仍会筛选/排序一次；若此前已有一次成功的局部筛选渲染，则紧接着的第一次翻页即可复用，此后连续同条件翻页继续复用。任何实际到达显式 filter、排序/品质/生存条件变更、查询提交或清除/重设处理器的调用都不传 `pageOnly`，即使值与上次完全相同也强制重新选择；局部 DOM 更新失败并回退时，刚准备的结果也会被清空。命中只省去 `selectInventoryItems` 的重复筛选/排序，当页比较、完整页 HTML 和 DOM 更新仍执行，视图另有装备及数量统计遍历，不能描述为“所有翻页均命中”或“翻页零全背包扫描”。

正确性依赖“已提交对象不被原地改写”的现有应用约束：模块不观察 item 字段变化、同数组 push/splice，也不比较 `revision`、数组长度或内容；只原地修改这些值后直接 `pageOnly` 读取，可能沿用旧成员/顺序。普通无注入选择结果的 `center(s, ui)` 和显式非 `pageOnly` 读取仍会看到新内容，但不能替缓存使用者自动失效。未来若增加原地修改路径，必须在下一次分页读取前替换 state/物品数组、明确清空缓存或强制一次新选择；调用方也不得对返回的缓存数组原地排序、增删或改写物品。当前成功事务由引擎产生新 state、保存后替换并渲染，主存档失败的 `act` 分支虽保留旧 state 也会全页重绘清空，镜像警告属于已成功提交的结果；只在对话框中报告且未改变已提交 state 的导入失败不必额外清空。成功导入、换局、恢复读取，以及普通跨标签差异存档同步都会替换 state 并全页渲染；缺失/损坏或删除重建异进度进入恢复保护时也会全页渲染。跨标签事件不能概括为“一律失效”：序列化完整 state 相同的事件会保留当前对象，若警告也未变则直接返回并允许继续复用；警告改变且非忙碌时的全页重绘才清空。所有交易报价、回收、确认与保存仍必须从完整当前 state 独立验证，不能使用这份展示选择结果作为交易依据。
