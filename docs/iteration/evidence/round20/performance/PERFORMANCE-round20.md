## 四、新增能力的 Node CPU 成本：固定 12 格

### 协议

12 格为装备数 3 / 100 / 1,000 / 10,000 × 赌桌 10 层 / 赌桌 30 层 / 许愿 140 层。每格每阶段 6 次 warmup、24 次正式样本，共 864 个正式时长、216 个 warmup 时长。三个阶段是输入完整 `gameView`、当前完整 `gameView`、当前风险模型。每轮旋转全部六种阶段顺序，原始样本全部保留。分位数统一为排序后 `floor((n-1)*p)` 索引。

固定种子为 `20261020 + floor`，有效构造状态使用等级 80、金币 100,000、规定库存数量，以及可用时最新的五件装备。通过修改首个已生成路线格的事件类型，再调用原始进入动作建立待选择场景；这是合法保存形状的压力夹具，不是自然走到这些房间的玩家记录。

独立模型阶段对赌桌计算 roll + safe 两个 quote，对许愿计算 roll 一个 quote。此时完整视图的主面板与按钮摘要各自计算 quote，故赌桌完整视图调用四次风险预览、许愿两次。模型阶段和完整 HTML 阶段的职责不同，不能直接当成同一工作量。

正式时长来自无探针的原始对象。所有计时结束后，才在另建的克隆状态上安装装备 id 读取计数器；它仅证明访问量，不代表分配量、总指令数或真实时间。每次结果的全文哈希稳定，每格调用者完整 JSON 不变；所有 `src/**/*.js` 与测量脚本前后哈希稳定。

根代理已确认正确性 CPU 与功能浏览器任务结束，本代理的深层模拟也已结束，才开始本批次；根代理正式页面测量在此批次之后运行。主机为 Node v24.19.0、AMD EPYC 9V74。共享宿主机其他活动和垃圾回收不可完全控制。

### 访问量与可行动的原因

| 10,000 件场景 | 输入 HTML id 读取 | 当前 HTML id 读取 | 独立模型 id 读取 |
| --- | ---: | ---: | ---: |
| 赌桌 10 层 | 473,626 | 968,522 | 247,448 |
| 赌桌 30 层 | 473,626 | 1,568,354 | 547,364 |
| 许愿 140 层 | 457,374 | 872,262 | 207,444 |

每格当前比输入增加的 id 读取数，正好等于该格独立模型阶段的两倍，吻合主面板和按钮重复求同一 quote 的代码路径。模型通过公开赔率读取当前装备属性，库存尾部装备会使读取量随库存增大。

这组数据提出的候选是在单次同步渲染内复用同一状态、同一 choice 的 quote，避免主面板与按钮摘要重复计算。需保留独立调用的默认行为，以及确认弹窗按当时状态重新报价的语义，不引入跨状态全局缓存。root 随后实施了这个范围内的局部复用；首批数据仍作为未复用版本原样保留，后续验证见第六节。

原 Round 16 的重复排序实验已经出现过 Node 加速但浏览器退化并回退，不应重做后宣称成功。本轮候选应局限于这次新能力增加的实际重复计算，并以页面实测判断取舍。
