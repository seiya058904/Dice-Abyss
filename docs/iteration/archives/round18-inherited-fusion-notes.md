# Round 09 · 融合费用语义

本文件记录本轮费用反馈差异；完整工作台设计与历史性能仍保留在早轮证据。当前数值公式、收益六骰面、材料保护、权威交易与RNG均未改变。

| 权威报价/余额 | 当前界面 | 主动作与恢复 |
| --- | --- | --- |
| 费用≤金币余额且≤GOLD_CAP | 完整费用与非负余款 | 按既有保护规则确认/结算 |
| 费用≤GOLD_CAP但余额不足 | 明确差额和“无法结算” | 保留原按预算调整材料，不硬禁用此恢复动作 |
| 多材料总价>GOLD_CAP、单件≤GOLD_CAP | “费用超过持有上限”，上限10,000,000,000 | 结算真实disabled；减少材料或更换目标 |
| 单件本已>GOLD_CAP | “单件材料费用超过金币持有上限” | 换目标；不误导玩家补1金币，也不让失效提交清空选择 |
| 费用恰好GOLD_CAP、余额GOLD_CAP | 可以支付，预计余款0 | 原生投骰提交/刷新与完整引擎结果一致 |

超过上限时，equipment.js使用的GOLD_CAP+1只表示“不可支付”；不应向玩家展示为精确实际价格。当前UI不改变该内部协议，也不计算一条新的费用规则。

新6项fusion-gold-cap用例在输入版均失败，当前与原controller/workbench共17项通过。qa-fusion-cap-browser.mjs覆盖4类费用×1366×768和375×812，共8场景/218断言，0page/console error；只使用校验器接受的构造存档。恰好上限的组合为角色Lv5870、目标Lv4945533，真实提交扣到0，其他结果与原引擎一致。视口模拟不是自然达到该等级或实体手机证明。
