## 2. 选择依据与实际变化

### A. 搜索全背包，同时看清回收范围

原背包只能按装备位、品质和排序翻页，难以按名称找到晚页装备。本轮增加原生名称搜索表单：去除两端空白、大小写不敏感的字面子串；先对全背包组合条件，再沿原稳定排序分页，每页仍为 60 件。输入只改草稿，不逐键重绘或写存档；提交才应用。清除名称保留槽位／品质，清除全部同时复位；普通导航与同一 run 同步保留草稿，专用战败备战入口及新 run 清空过期查询。

搜索附近明确写出“全背包检查（不受搜索与筛选影响）”，保留只回收弱于当前装备的普通／稀有旧装，以及装备／锁定／本次战利品的保护。浏览器实际搜索第 10,000 件装备，再取消／提交完整回收，核对主镜像、刷新和失败回退。没有把名称筛选误当删除范围。

7 项新回归通过。六个逻辑视口的搜索最终 10/10 组、171 检查通过；初次真实渲染发现 1366 控件继承约 9.8 px 字号，补最小 12 px 后复验。原始失败与驱动修正都保留。原生键盘已测，系统中文 IME 未验收。

### B. 消除批量回收预览中反复扫背包

输入的多 ID 分支对每件目标执行 `items.find`，万件低品质批次产生 48,808,996 次 ID 读取。本轮只在多 ID 预览内建立局部 Map，保留重复库存 ID 的首对象、请求顺序和原引用；单 ID 继续原 find；实际删除既有 Set 逻辑不变。相同万件低品质批次变为 39,504 次读取。

原 6 项回归在输入上为 5 通过／1 项查找复杂度失败，当前 6 全过。五场景的完整引擎、保存、顺序、保护、未知字段与回读均核对。真实浏览器另测两种万件背包，每场景 8 对正式＋2 对预热，共 40 行全部成功，无删样。混合回收 2,438 件的点击→主写返回 p50 **319.55→112.85 ms**，低品质回收 9,752 件 **914.40→80.05 ms**；每场景 8 对在主写返回及写后首／双 rAF 上均同向缩短。

这不是原生存储本身提速：`setItem` 均值和尾部有负向；32 正式行仍各有 1 Long Task 和 1 次 >50 ms rAF。setItem 返回不是物理磁盘 flush，rAF 不是已绘制或 FPS。完整协议及所有负向见 PERFORMANCE。

### C. 恢复记录服从这一掷是否真正存活

旧两类恢复说明在判定完整反击及后置流失之前即写“已触发”，某些致死掷的 lastRoll 因而记录了没有生效的恢复。本轮先保留说明和原位置，生死确定后再插回，且早于两处 24 条截断；死亡改为“未生效（本掷未存活）”。生存文本、数值合计／取整、顺序、RNG 消耗和旧存档历史均保持。

7 项新回归通过。最终冻结引擎真实跑 224 对：50 个死亡状态的 53 条说明纠正，174 个其他完整状态逐字相同；896 次编解码回读成功。这里改的是恢复记录真值，死亡页面本身并不呈现全部 mechanics。较早报告的 engine SHA 过期后已重跑 final 版，而非只改报告身份。
