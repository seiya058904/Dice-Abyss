## 4. 清单、重解压与真实启动门禁

`FILE_MANIFEST.json` 按项目相对路径稳定排序，逐文件记实际字节与 SHA-256，只排除其自身。ZIP 使用普通 DEFLATE，不分卷，不以链接占位，保留原启动入口执行位。所有源文件和资源真实包含在完整包中。

首次组装在原验证器的清单门禁被拦截：生成器使用 Python Path 的分段排序，与完整 POSIX 相对路径字符串排序不同。没有重复路径或游戏源码变更。组装器改为显式按 `row.path` 字符串排序后重建；[原始失败与定位](evidence/round14/validation/packaging-attempt-01/diagnosis.json)连同未改写的失败日志保留。验证器及排序断言未放宽，必须对新实体从头重跑。

原 `scripts/verify-package.py` 对实际交付 ZIP 检查严格 50MB、中央目录/安全路径/类型/展开预算、CRC、完整清单集合、每项长度与 SHA、package/index/STATE 版本，然后真正写入此前全空目录并逐文件复核解压字节。独立复审者随后从该新目录运行 `npm run check`、全部细项测试和真实 HTTP 资源检查；最终预期 **588 项**，这里不提前记录成功。只在所有发布门禁实测通过后交付；若失败，修复后重新生成清单/ZIP并对新的实体重跑。

包内记录区分首完整候选 587 项与最后冻结后 17 项定向检查；最终 ZIP 的完整 TAP/HTTP/CRC 回执在包外产生。这样不会用早期结果冒充最终成品测试，也不会在最终验收后回写并改变已通过测试的 ZIP。详细命令和范围见 [VERIFY](VERIFY.md)，性能的未归因变慢与软件 4K 长尾仍按 [PERFORMANCE](PERFORMANCE.md) 公开保留。
