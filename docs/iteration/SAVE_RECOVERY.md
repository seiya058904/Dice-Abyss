# Round 13 · 存档丢失后的完整进度保护

## 玩家会遇到什么

运行中的页面若收到另一同源窗口清空或删除存档的通知，会重新读取主存档和镜像。两份都已消失或无法读取时，游戏进入专门的“存档保护”页面。页面保留最后一次**已经提交**的完整内存进度；如果掷骰结果已保存、画面还在演出，备份包含已提交结果，不回退到演出前的显示状态。

第一步是“导出本页完整备份”。页面列出旅途标识、层数、等级、装备数、金币、战斗掷骰数和操作次数，帮助区分进度。短旅途标识具有完整的title和可访问名称；备份本身保留完整runId、未知嵌套字段、待领奖内容及全部其余状态。

若浏览器又出现可读进度，保护页同时展示这份候选，旧内存仍可导出。只有玩家明确确认“读取浏览器进度”，本页才使用它。恢复与读取的确认框内也可先导出，Escape返回对应入口。保护页说明在恢复或导出前应保留页面；它不能在页面已经关闭后重新构造丢失的内存。

## 三种状态与写入边界

| 当前记录状态 | 页面入口 | 是否写入 |
| --- | --- | --- |
| 主和镜像均为真正的null，且没有可恢复的旧版记录 | 导出本页备份、重新检查、确认恢复 | 只有确认后取得已有写锁，原始两串仍为null/null，并通过原saveGame校验时，才写完整主存档及镜像。 |
| 仍有一份可读存档，包括有效镜像或旧版恢复路径 | 导出本页备份、查看候选、确认读取、原始记录导出 | 检查与读取均不写档；确认读取时，锁内再次要求两份原始字符串和展示候选时完全相同。 |
| 存在空字符串、损坏内容、无法取得完整原始记录或其他无法读取状态 | 导出本页备份、可取得时导出原始记录、重新检查 | 不提供覆盖已有记录的恢复权限；不将空字符串当null，不自动删除或修复损坏原串。 |

保护页内存和浏览器记录是两份不同的来源。原始记录导出使用 `dice-abyss-raw-records` 标识，保存两个键的完整原文；页面明确该诊断文件不能直接当普通游戏存档导入。普通“本页完整备份”仍是现有合法游戏封套。

## 排队通知与重复事件

实际浏览器将storage通知排进任务队列。另一页可能在一次任务中先clear，再立即写入新主档与新镜像；旧页接到删除通知时，磁盘已经有效。最终处理使用明确的删除通知（null key或newValue严格为null）加完整当前状态比较：若内容不同，把磁盘版本作为候选，仍保护原内存。相同runId/revision但未知字段不同也属于不同进度。

若通知实际检查时，浏览器已再次可读取与本页完全相同的完整状态，延迟到达的clear、remove及后续set通知只更新镜像告警，不中止正在播放的演出或确认框。普通的不同进度写入通知继续沿用原自动同步；这个完整比较只在跨页storage事件执行，不新增到每帧、本页render或每次保存路径。

另一标签的一段同步JS不是跨标签原子事务。旧页若确实观察到短暂的null/null，会正确进入保护；之后即使原样进度再次出现，也保留显式读取步骤，不自动恢复已取消的确认。原生审计记录实际读取原串来区分这两种情况。

sessionStorage即使使用相同键名也不参与localStorage同步。无关键直接忽略。当前页面自身的clear不会由浏览器回发storage事件；本页随后写入仍受原完整expected校验约束。本轮没有声称操作系统清理、页面关闭、电源中断或不合作的外部任意写入能够被原子恢复。

## 事务与交互保护

- 进入保护时取消旧pending、确认框、融合浮层和正在展示的视觉状态，增加动画代际以拒绝迟到回调；完整已提交state保留。
- 主动作、Space、新局、导入，以及已经开始读取文件的异步导入都在必要边界检查保护态；锁内再次检查，旧确认不能绕过保护。
- 恢复沿用 `dice-abyss:save-write`、原saveGame、完整expected语义、schema5、迁移、归档顺序及5,000,000字节新写入边界。镜像写失败仍明确告警，主档失败不部分提交。
- 快照持有两份原始字符串；只看runId、revision、checksum或解码后“看起来一样”不能授权读取已改变的原始记录。
- Web Locks只约束使用同一锁的协作窗口；localStorage不是通用原子compare-and-set接口。

独立25格矩阵覆盖主/镜像各为null、空串、损坏JSON、V4、V5的所有组合：只有null/null一格可以恢复，其余24格均零写入。另有原串仅加空白、对象所有权隔离、损坏归档和读取异常等专项。具体测试结果与原生事件、导出、锁竞争证据见[VERIFY](VERIFY.md)。

## 明确的限制

完整二元原文无法取得时采用保守保护。人工注入“仅一个键的getItem抛异常”的环境可能让新诊断停留在保护页；原loadSave的单副本降级代码未改。没有实际浏览器证据支持为这种局部异常绕过原文比较。

清空操作已经删除的升级前旧档原文不能由迁移后的schema5内存反推重建。当前内存仍完整可导出，但本轮不会捏造旧原文或历史归档。近上限存档、同步保存成本、真实设备与后台行为继续按[BUG_LEDGER](BUG_LEDGER.md)保留限制。
